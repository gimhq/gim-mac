## Context

The repository holds only `README.md` (commit 59e1b24). The product spec is
phase 6 of `gim-core/docs/plan/20261022-repo-split-client-sdk-mac-web.md`
(user decision 2026-10-22: native macOS, benchmarked against Telegram for
macOS; SwiftUI with AppKit where SwiftUI falls short, such as text input,
very long lists and window management). Wording, settings structure and
languages are shared with every client and defined by the Android plan
`gim-android/docs/plan/20261023-0755-product-ui-i18n-settings.md`; the
workspace ledger `gimhq/docs/plan/20261023-0953-clients-product-alignment.md`
names the cross-repo contracts C1 to C7.

  of the gim-core API (`GimClientAPI`, 60 methods, `GimClientFactory`,

  data; `GIMFeatures` holds the view models (chat list, timeline, composer,

## Proposal

### Architecture

- Swift 6, macOS 15, xcodegen `project.yml`, bundle id prefix `im.g`. Project,
  target and scheme are named `GIM` (same gate pattern as gim-ios); the app's
  bundle id is `im.g.mac`, `PRODUCT_NAME` `GIM`, display name "gim". One app
  target `GIM` (`GIM/Sources`, `GIM/Resources`) and one unit-test target
  `GIMTests` (`GIM/Tests`). No extensions, no signing, no notarization, no
  Sparkle, no App Store work.
- Packages: `GIMKit` by local path `../gim-ios/Packages/GIMKit` (products
  `GIMClientKit`, `GIMFeatures`). On station the worktree layout does not
  contain `../gim-ios`; only the Mac host builds, and the gate lays the two
  trees out side by side (below). `GIMCore` (contract C5) is added to
  `project.yml` as a package only when the workspace coordinator forwards it.
- Client seam: `AppModel` owns one `any GimClientAPI` made through a
  `GimClientFactory`. Today the only factory is the fake one
  (`FakeGimClient`); `RealGimClientFactory` for GIMCore is a documented
  follow-up with the same shape as gim-ios's `GIMPlatform/Bridge`.
  `PlatformHooks` for macOS: Keychain secure storage, Application Support
  data directory (`~/Library/Application Support/gim`), reachability.
- Views are SwiftUI; AppKit is used through `NSViewRepresentable` for the
  composer text view (`NSTextView`) and wherever lists or windows need it.
- Strings: a String Catalog per feature, used as tables (`App`, `Explainer`,
  `Onboarding`, `Chat`, `Settings`), `String(localized:table:)` and
  `Text(_:tableName:)`; no hard-coded user-visible text. Code keeps the old
  terms (hub, handle, user ID); only user-facing text uses the glossary words
  (server, username, Account ID, recovery key, remove device, connected / not
  checked, main server). One table per workstream keeps merges conflict-free.
- Windows and commands: a `WindowGroup` for the main window (sidebar chat
  list plus chat pane, `NavigationSplitView`), a `WindowGroup(for: ChatID)`
  to open a chat in its own window, a Settings scene (Cmd+,), and a
  `MenuBarExtra` for menu bar mode. Menu commands are composed from one
  `Commands` type per feature (`AppCommands`, `ChatCommands`,
  `SettingsCommands`) so each workstream edits only its own file.

### Workstreams (one L2 each, disjoint write scopes)

**W1 shell-gate** (first; everything else branches after it is in `main`)

- `project.yml`, `.gitignore`, `README.md`, `docs/glossary.md` (the shared
  glossary adapted to macOS wording: accessibility labels instead of
  `contentDescription`, String Catalogs instead of string resources).
- `scripts/mac-gate.sh build-test [--sha <commit>] [--keep]`: ships
  `git archive <sha>` of gim-mac to `~/gim-ci/<id>-<short sha>/gim-mac/` and
  `git -C $GIM_IOS_REPO archive $GIM_IOS_REF Packages/GIMKit` (defaults
  `/srv/gimhq/gim-ios`, `HEAD`) to `~/gim-ci/<id>-<short sha>/gim-ios/`, so
  the relative package path resolves; takes the shared lock; runs `xcodegen
  generate`, `xcodebuild build` of the app, `xcodebuild test` of `GIMTests`,
  and `swift test` of GIMKit (the package tests); copies logs and xcresult
  bundles back to `.tmp/mac/<short sha>/`; prints one `[mac-gate] mode=
  build-test sha=<short> ios=<gim-ios short sha> build=ok|fail app-tests=
  ok|fail kit=ok|fail` line; exits non-zero on any failure. `GIM_GATE_ID`
  defaults to the last path component of the branch name.
- App shell in `GIM/Sources/App/` (`GIMApp`, `AppModel`, scenes, `AppCommands`,
  keyboard navigation between sidebar and chat pane), `GIM/Sources/Platform/`
  (platform hooks, client factory selection), `GIM/Sources/Sidebar/` (chat
  list from `ChatListViewModel` with `ChatRow`, unread badges, selection,
  "open in new window"), `GIM/Sources/Shared/` (design tokens, avatar with
  initials and stable colours, `ExplainerView` with the six "How gim works"
  sections in `Explainer.xcstrings`), and stubs that later workstreams own:
  `GIM/Sources/Onboarding/OnboardingFlow.swift` (placeholder that signs in
  with the fake client), `GIM/Sources/Chat/ChatPaneView.swift` and
  `ChatCommands.swift` (placeholder pane), `GIM/Sources/Settings/
  SettingsScene.swift` and `SettingsCommands.swift` (empty settings window).
- `GIM/Tests/` with the first app unit tests (AppModel sign-in through the
  fake client, chat selection, window routing).
- Acceptance: `scripts/mac-gate.sh build-test` green; the app launches into
  the sidebar + pane layout with the fake client's demo data; a chat opens in
  a new window; menu bar has App, File, Edit, View, Window, Help with
  working shortcuts for new window, close, settings, and chat navigation.

**W2 onboarding-account** (after W1; parallel with W3 and W4)

- `GIM/Sources/Onboarding/**`, `Onboarding.xcstrings`, their tests.
- Onboarding starts with "Link to existing device": a QR code (CoreImage)
  from `startLink` with the SAS confirmation (`waitLink`, `confirmLink`), a
  copyable link code as the fallback. Then "Create account" (name first;
  the server step is skipped when a default server exists, "Use another
  server" under a small link) and "Restore": paste the recovery kit text
  into one field, separate Account ID and recovery key fields as fallback.
  Three short intro pages reuse `ExplainerView`.
- Recovery kit (contract C2): kit text (title, "Account ID: …", "Recovery
  key: …" grouped, blank line, note), label-independent parser, last-4
  check, copy and save as a text file. The SDK ships this since
  gim-client-sdk main 04a02b5 (`format_recovery_kit`, `parse_recovery_kit`,
  `recovery_key_ending`, `matches_recovery_key_ending`; see
  `gim-client-sdk/docs/API.md` and `bindings/gim-ffi/generated/swift`), but
  gim-mac links no SDK build until contract C5 lands. Until then: reuse the
  GIMFeatures implementation when gim-ios has landed one in
  `../gim-ios/Packages/GIMKit`; otherwise implement it in
  `GIM/Sources/Onboarding/RecoveryKit.swift` with the identical text format
  and tests mirroring the Android cases. Either way W2 records "swap to the
  SDK functions once an SDK build is vendored" as a follow-on item in its
  final report (no new scope).
- Default server: last used, else the `-GIMDefaultServerURL` launch argument,
  else the `GIM_DEFAULT_SERVER_URL` build setting (as gim-ios).
- Acceptance: with the fake client, link, create and restore each reach the
  main window; a kit written by this client parses back; the Android sample
  kit text parses; gate green.

**W3 messaging-media-search** (after W1; parallel with W2 and W4)

- `GIM/Sources/Chat/**`, `Chat.xcstrings`, their tests.
- Chat pane: fast message list on `TimelineViewModel` with infinite scroll
  through `paginateBackwards`, grouping by sender and time, date chips,
  status ticks, replies, reactions, edit and delete, read marks, typing
  indicator; composer on `NSTextView` (Enter sends, Shift+Enter newline),
  attachments; drag and drop of files and images onto the pane and paste of
  images into the composer go through `MediaPreparation` and `sendMedia`;
  Quick Look (`QLPreviewPanel`) for media and files; chat list search in the
  sidebar toolbar and message search within the open chat (client-side over
  the loaded timeline); link previews fetched client-side from the page's
  Open Graph tags, cached, never through the hub; new direct chat by
  username, new group, group info (the contacts view models) from the
  sidebar toolbar, as every client has. New chat also has "Scan QR code"
  next to the username search (contract C8): a QR image pasted or dropped,
  or captured with the Mac's camera when one is available, is decoded with
  Vision; any text that contains a valid Account ID token (regex above)
  starts a direct chat with that user through `createDirectChat`; pasted
  plain text with an Account ID works the same way. `ChatCommands`: message
  actions and navigation shortcuts.
- Acceptance: each item above works against the fake client; message list
  stays smooth with 10k demo messages (pagination, no full reload on diff);
  gate green.

**W4 settings-system** (after W1; parallel with W2 and W3)

- `GIM/Sources/Settings/**`, `GIM/Sources/System/**`, `Settings.xcstrings`,
  `project.yml` entries needed for notifications and launch at login, their
  tests.
- Settings window (Cmd+, and the avatar in the sidebar) with the shared
  sections (contract C4): Profile (name, username claim / change / remove,
  Account ID with copy, "My QR code" that encodes the plain Account ID
  only, contract C8); Account and devices (what the
  recovery key is, linked devices via `DevicesViewModel`, remove device, link
  a new device by pasting its link code and confirming the SAS through

  zh-CN, zh-TW, es, applied through `AppleLanguages` with a relaunch prompt);

  version, licences); Sign out with a confirmation that says the recovery
  kit is needed to come back. Account-safety entries (C7) have their place

- System integration: local notifications through `UNUserNotificationCenter`
  for new messages while the app is not frontmost (title, body, thread per
  chat, click opens the chat), dock badge from the unread count; the APNs
  path is a later step when a provider exists. Launch at login
  (`SMAppService`). Menu bar mode (`MenuBarExtra` with unread count and a
  chat list; "hide dock icon" via the activation policy).
- Acceptance: every section works against the fake client, the hidden C7
  entries have no fake behaviour, a message arriving in the background
  shows a notification and updates the badge, launch at login toggles,
  menu bar mode shows and opens chats; gate green.

## Risks

- The Mac host and the whole Tailscale range did not answer from station at
  planning time. If it stays unreachable, W1 cannot run its gate and the
  campaign stops at the first hard stop (decision event to the user).
- `GIMFeatures` is being rewritten by gim-ios while this campaign runs: view
  model names and shapes can change between L3s. Each L3 builds against the
  gim-ios `main` of the moment (`GIM_IOS_REF`), and a break caused upstream
  is reported as a cross-repo need, not patched in a fork.
- The recovery kit may be implemented twice (gim-ios's GIMFeatures and
  `GIM/Sources/Onboarding/RecoveryKit.swift`) until the SDK ships it through
  the FFI; the swap is recorded as a deferred item.
- Translations written here need a native-speaker review before release.
- The real-client bridge, APNs, UI tests against a hub, signing,
  notarization and distribution are out of scope and remain for later plans.

## Scope

In: the five workstreams above, inside `/srv/gimhq/gim-mac` only.

Out: anything in sibling repositories; signing,
notarization, Sparkle, App Store; the real GIMCore wiring (follows contract
C5); APNs; UI tests against a hub; account-safety features (contract C7).

## Alternatives

- One Xcode project with a local copy of GIMKit instead of a path
  dependency on gim-ios: avoids the side-by-side layout on the Mac host but
  forks the package, which the user ruled out (contract C6).
- A single `Localizable.xcstrings`: simpler lookups, but every workstream
  would edit one JSON file in parallel and merges would conflict.
- Serial workstreams only: no merge risk, but about three times the wall
  clock; the stub files owned by W1 make the parallel split safe.
